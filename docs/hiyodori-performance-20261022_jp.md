# hiyodori の GPU 比較・OpenMP 測定（2026-10-22）

この記録は既存の計算実装を変更せずに行った性能測定をまとめる。
結果・入力ハッシュ・条件の機械可読な要約は
[測定要約 JSON](hiyodori-performance-20261022.json) を参照。
実行ファイル、入力波形、個別ログ、全イベント出力はコミットせず、
ワークスペースの `results/` に保持する。

## 実行環境と条件

- hiyodori：AMD EPYC 9334、物理32コア／論理64スレッド、
  NVIDIA RTX PRO 4000 Blackwell、ドライバー595.99.02、波形はNFS NAS上。
- 過去のRTX PRO 2000 Blackwell／Threadripper 3990Xの記録を参照した。
  ホスト名aogeraはユーザー提供の情報で、過去のmanifestには物理GPUの識別情報がない。
- ソース作業ツリーは `816af76`。本計算は記録上 `5153085` の既存実行ファイルを凍結コピーして使用。
  当時のmanifestとバイナリSHA-256は一致するが、manifestの
  `source_revision_verified=false` は変更しない。
- CUDA、GPU Bootstrap、3成分、要求周波数0.1–0.25 Hz、実効下限0.099609375 Hz、
  探索格子67×67、刻み0.005 s/km、各軸の最大0.165 s/km。
- 新規測定は順次実行。OSキャッシュは消去せず、設定ごとの慣らしを除外。
  GPU計算プロセスを各実行の前後に確認した。アフィニティ調整は行っていない。

## 過去のRTX PRO 2000との比較

短い比較は `e0e0c4d` を独立ディレクトリに再構築し、
2004-04-01の固定乱数・固定FFTWドライバを使用した。
16 OpenMPスレッド、各モード慣らし1回＋測定5回。
GPU Bootstrap有効時の中央値を示す。

| 処理 | 過去のPRO 2000 | hiyodoriのPRO 4000 | 時間比（過去／今回） |
| --- | ---: | ---: | ---: |
| 全体 | 13.890511 s | 12.045468 s | 1.153× |
| Slant stack | 0.810540 s | 0.388327 s | 2.087× |
| Bootstrap | 0.551372 s | 0.427437 s | 1.290× |

CPU Bootstrap／GPU Bootstrapの慣らしを含む全12実行で、
6イベント、137受理窓、初期候補と過去出力の比較に合格。
比較は既存のbeam `rtol=1e-4`、Bootstrap `rtol=1e-3`、
残差 `atol=1e-12` などの規則を保持した。
CUDA Slant stack・powerの既存回帰チェックにも合格した。

本計算の比較対象は2013-01-01〜14、選択閾値R/T/U = 3/3/15、117イベント。
1月15日まで実行し、ログの1月1日 `#Start` から1月15日 `#Start` の差を計測した。
1月15日の処理は区間時間に含めない。

| 対象 | 過去（1回のみ） | hiyodori（5回の中央値） | 今回の最小–最大 |
| --- | ---: | ---: | ---: |
| 14日分の区間時間 | 289.773913 s | 214.366512 s | 214.186487–214.553618 s |

観測された時間短縮は26.02%（1.352倍）。ただし過去の本計算は、
別のRTX PRO 2000 CUDA実行と実行時刻が重なる。
同一の物理GPUかは確認できず、CPU・ストレージ・負荷の差も含まれるため、
この比率をGPU単体の性能比として扱わない。

## hiyodori の OpenMP スレッド数比較

こちらは現在の本計算と同じ版のドライバで、選択閾値R/T/U = 3/3/15を使用。
上の歴史的6イベント測定とは版とイベント選択条件が異なるため、
短い測定の全体時間を混在させない。
`OMP_DYNAMIC=FALSE`、`OMP_PROC_BIND` と `OMP_PLACES` は未指定。

| OMPスレッド数 | 2004-04-01、5イベント、各5回の中央値 | 2013-01-01〜14、117イベント、各3回の中央値 |
| ---: | ---: | ---: |
| 16 | 10.643096 s | 214.625713 s |
| 32 | 10.440504 s | 210.499602 s |
| 64 | 10.594760 s | 未測定 |

32スレッドは16に対して、短い検証で1.904%、本計算で1.922%短縮。
本計算の測定範囲は16スレッドが214.098408–215.342363 s、
32スレッドが209.839589–211.185477 s。
64スレッドは短い検証で32より遅かったため、本計算は16と32に絞った。

短い検証では、16→32でフィルタ0.167300→0.085785 s、
QC 0.330071→0.215551 s。全18実行のイベント出力はバイト単位で一致し、
受理窓・初期候補も一致した。
本計算の慣らしを含む全8実行は117イベント・受理窓と既存出力比較に合格。
通常の時刻依存Bootstrap乱数を維持するため、既存の比較ツールと同じく
21–32列を比較対象から除外し、非有限値は許容していない。

今回の測定範囲では32スレッドが有望。ただし運用中の設定ファイルは変更していない。
Hessianの窓バッチとCPU 3成分Bootstrapには最大16並列の制限があり、
OMP数だけ増やしても全処理が32並列になるわけではない。

## 入力処理と先読みについて確認できたこと

32スレッドの短い検証の中央値は、入力全体6.368750 s、
`read_decode_copy_s=6.208530 s`、フィルタ0.085785 s。
`read_decode_copy_s` はHDF5読み込み・伸長・変換・コピー・メタデータ処理を含み、
純粋なNAS転送時間ではない。
本計算32スレッドの入力段階は14日合計93.192627 s（各実行の合計の中央値）。
独立に求めた段階別中央値は、全体中央値と厳密には加算一致しない。

既存 `prefetchFile()` は、翌日のファイルへ
`posix_fadvise(fd, 0, 0, POSIX_FADV_WILLNEED)` を発行する。
今回の本計算と同じバイナリをCPU設定で短時間追跡し、1月1日の読み込み前に
1月2日ファイルへ `fadvise64(..., POSIX_FADV_WILLNEED) = 0` を確認した。
これはOSへの依頼の成功であり、全ファイルの先読み完了や有効量を実測したものではない。
翌日分のHDF5展開・フィルタまで完了させる非同期パイプラインは未実装。
詳細は[先読みの保留記録](cpu-io-optimization_jp.md)を参照。

過去のMacの入力1.080 sは別の入力条件のキャッシュ済み測定で、実ディスク読み込み0 byte。
USB4 SSD対NASの転送速度だけで、今回との差を説明しない。
Macとの比較には同一ファイル・成分・版・キャッシュ条件での再測定が必要。
