# bootstrap並列化とピーク探索の統合検証

ピーク探索・倍精度化・丸めでの終了判定を `dc38340` としてコミットした。
GitHubの `origin/main` に追加された3成分CPU bootstrapのOpenMP並列化は `49dbb27`。
`test/peak-search-boundaries` で `git pull --no-rebase --no-edit origin main` を実行し、
競合なく `b0ce192` として統合した。
以下では、ピーク探索・Newton法の修正が完了した直列版と統合版を比較する。
修正前の旧カタログを比較基準にしたものではない。

統合後のピーク探索、Newton法、丸め終了判定、共分散変換の関数は `dc38340` と文字列一致。
bootstrapバッチ並列化の関数は上流と一致した。
独立したサンプルを並列評価し、その後は元の順でパワーを集計するため、
ピーク選択や4×4の計算式への直接の変更はない。

実行ファイルと関連テストを再ビルドし、拡張されたbootstrapバッチ検証を含む
計算・workspace関連の13テストが通った。
検証ツールのテストもサンドボックス外で再実行すると通った。
初回の失敗は、macOSの `/usr/bin/time -l` が `sysctl kern.clockrate` を呼ぶことに対する
実行環境の制限で、`/usr/bin/true` を計測しても同じ失敗になった。
選択したCTest 14件について合格結果を確認済み。
詳細ログはGit管理外の `docs/benchmarks/bootstrap-peak-integration-20260917/` に保存した。

## 実データの一致確認

統合版の検証ドライバでHi-netの2005年3月15〜17日を再実行した。
3成分、0.1〜0.25 Hz、slowness範囲 ±0.165 s/km、刻み0.005 s/km、CPU 8スレッドを使用。
波形・カタログのハッシュ、品質判定履歴、bootstrapの固定乱数
（`1837 + 104729 * replicate`）、FFTW設定（`ESTIMATE | UNALIGNED`）は、
保存済みの最終ピーク探索・Newton版と同一にした。
初日の品質判定履歴を維持するため、3日間全体を再計算した。

- 145イベントの全38列がバイト単位で完全一致した。
  各成分のエネルギー・共分散・bootstrap出力を含み、出力はすべて有限値だった。
  これらの出力から求めるエネルギー比も一致する。
- 初期候補147件、記録された最適化の全ステップ・結果・丸め終了の記録が一致した。
  受理された窓も一致した。
- max/MAD > 7（R/T）、> 35（U）で選別した75件（R31/T10/U34）も同一。
  前回復元したR候補も保持された。
- 修正済みスペクトル行列のカタログ、および検証用の旧行列による対照カタログは、
  それぞれ独立に実行した直列版の結果と完全一致した。

この結果は、検証済みのピーク探索・精度変更とbootstrap並列化を組み合わせる根拠となる。
すべてのイベントでの妥当性や、GPUバックエンドの検証を意味するものではない。

## CPU速度測定

`dc38340` と `b0ce192` の運用ソースに、固定乱数と共通の決定的なFFTWオブジェクトのみを
適用した実行ファイルで比較した。数値監査の追加計算や収束ログは含めない。
両版とも同じRelease/O3のClangビルドとプロファイル設定を使用した。

Apple M4 Max（16コア）で2005年3月15日を、OpenMP 8スレッド、3成分、
同じ周波数・slowness設定で計算した。各版1回の慣らし実行を除外した後、
各5回を交互の順で、新しいプロセスとして実行した。
OSキャッシュは消去せず、測定中に他のエージェントのビルドやテストは走らせていない。
慣らしを含む全12実行で、同じ46イベントがバイト単位で完全一致した。
入力のハッシュも実行前後で変わらなかった。

| 経過時間の中央値 | bootstrap並列化前 | 統合版 |
| --- | ---: | ---: |
| プロセス全体 | 110.92秒 | 56.14秒 |
| bootstrap部分 | 64.73秒 | 10.05秒 |
| グリッド部分 | 4.149秒 | 4.131秒 |

bootstrapは**6.44倍**、全体は**49.39%短縮**（1.98倍）だった。
全体の実測範囲は変更前110.54〜117.23秒、変更後55.88〜56.17秒。
最大RSSは両版とも約2.39 GiBだった。
事前の採用基準である「全体・グリッドの中央値の悪化が5%以内」、
「bootstrapが10%以上改善」、「イベント出力の完全一致」をすべて満たした。
この値は、このマシンでの1日分のCPU計算に対する測定結果である。
スレッドごとの呼び出し時間の総和は経過時間ではないため、速度比の計算には使わない。

## 再現と適用範囲

検証した統合版はmainへ取り込める状態と判断する。
インストール済みの運用バイナリへの反映には、通常のビルド・インストール手順が別途必要。

ローカルの検証資料ディレクトリに、ドライバ生成・比較・速度測定のスクリプト、
入力・ソース・バイナリのハッシュ、テストログ、実行結果を保存した。
詳細ログとイベントカタログはGit管理外に置く。
過去のドライバ生成スクリプトは特定時点のソースに依存するため、
統合後のコードで直接作り直すだけでは今回の検証手順の代わりにはならない。

通常実行のbootstrap乱数は、引き続き `time(0) * i` を使う。
式と抽出順序が同じでも、処理が速くなると実際のseedが変わり得る。
通常実行間のbootstrapの揺らぎを統合の不具合と混同しないよう、正しさの比較では乱数を固定する。
